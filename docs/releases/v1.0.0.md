# PageLoom OS — Release 1.0.0 (Discovery System, frozen)

**Status: stable, frozen.** This release is deployed and verified end-to-end in
production (`pageloom-os-production`). From this point forward, `main` moves on as
**1.1** — new work is built there, not on this release. A change to anything listed
below only happens as an explicit, deliberate bug fix, released as a `v1.0.x` patch
(see [Versioning policy](#versioning-policy) below).

## What's in 1.0

### Discovery system — unified onto the real backend
- The customer-facing Discovery questionnaire (`/discovery`) is the Google AI
  Studio–built frontend (`apps/web/src/ai-studio/**`), talking exclusively to
  pageloom-os's own backend and default Firestore database — no second Firestore
  project, no AI-Studio-native persistence layer.
- Real schema, unchanged: `organizations/{orgId}/projects/{projectId}/discoveryProgress/current`
  and `.../discovery/{sectionId}` (9 sections: business, customers, services,
  differentiation, trust, branding, materials, presence, goals), validated by
  `packages/core`'s `discoveryTemplate` — the same rules the server enforces.
- A field-level bridge (`apps/web/src/ai-studio/services/discoveryMapping.ts`)
  translates the frontend's flat `DiscoveryData` shape to/from that real schema.
- Owner/Admin console for Discovery: AI Studio's own `AdminMaster` view, reachable at
  `/discovery?view=admin`, role-gated, wired to real data.

### Required-field validation (real, not advisory)
- `apps/web/src/ai-studio/utils/discoveryValidation.ts` computes missing-ness by
  calling `packages/core`'s actual `missingRequiredDiscoveryFields` — never
  duplicates the rules, so client and server can't drift apart.
- Every step's Next button and the final submit CTA genuinely block on incomplete
  required fields, with per-field highlighting and inline messages (never a native
  `disabled` button — clicking while invalid reveals what's missing instead of doing
  nothing, which matters most on mobile).
- 19 unit tests pin the exact required-field set, including the either/or case
  (differentiation) and the shared-field case (presence.hasWebsite/hasDomain).

### Mobile UX
- 44px+ touch targets on the progress bar and review-step edit buttons.
- iOS safe-area padding on the sticky bottom nav; extra bottom clearance so a step's
  last field never sits flush against it.

### Owner Workspace — unified navigation
- One permanent 7-section sidebar: Dashboard, Customers, Discovery, Websites, AI,
  Billing, Settings (`apps/web/src/components/product-shell.tsx`), mapped onto
  existing routes (`/crm`→Customers, `/agents`→AI, `/projects`→Websites) rather than
  duplicating pages. Sales and the client-portal preview live in a secondary "More"
  block.
- New `/discoveries`: every Discovery org-wide, searchable/filterable, with actions to
  open the questionnaire or convert an orphan project to a real customer.
- New `/billing`: the first real, working billing surface — customers, invoices
  (using the previously-unused Israeli VAT calculator in `@pageloom/core`), and
  payments. Subscriptions is an honest "not available yet" state, not fabricated data.

### Backend Master — split into its own application
- `/master`, `/master/content`, `/master/customer` moved out of the Owner Workspace's
  `(product)` route group into their own `(master)` group with a separate shell
  (`apps/web/src/components/master-shell.tsx`) — no shared nav, no shared widgets.
  The Owner Workspace sidebar has zero reference to Backend Master.

### Progressive Web App
- Manifest: `id`, `scope`, `categories`, `shortcuts` (Dashboard/Customers/Discovery).
- Service worker (`apps/web/public/sw.js`): offline fallback shell
  (`apps/web/public/offline.html`) for failed navigations; version-update detection
  via `controllerchange`, surfaced as a dismissable "reload" toast, never a silent
  auto-reload (would risk losing unsaved input).
- Install prompt (`apps/web/src/components/install-prompt.tsx`): custom
  `beforeinstallprompt` handling for Chrome/Edge/Android, manual "Add to Home Screen"
  instructions for iOS Safari. Owner Workspace only.

### Owner notifications
- In-app notification center (existing `NotificationInbox`, now also a live
  unread-count badge on the topbar bell) fires for: Discovery started, draft saved
  (throttled to section changes, not every keystroke), Discovery submitted, files
  uploaded, and a new customer message (reusing the existing per-project comments
  endpoint).
- Shared `notify()` helper (`functions/src/notifications.ts`) — the single seam a
  future Firebase Cloud Messaging push send plugs into.
- FCM infrastructure (`fcmTokens` collection, `POST`/`DELETE /notifications/fcm-token`)
  is in place; push itself is **not yet configured** — see
  [External setup still required](#external-setup-still-required).

### Critical production bug fixes (found and fixed live, during verification)
1. **`/submit` transaction read-after-write** — `discoveryProgress/current` was read
   *after* section documents were already written in the same Firestore transaction,
   which Firestore forbids. Every real submission failed with a 400 until this was
   fixed — this may be the first Discovery submission in this project's history that
   was ever actually confirmed end-to-end.
2. **Frontend showed success without checking the server** — `handleSelectStep(9)`
   advanced to the success screen unconditionally while the actual submit call was
   fire-and-forgotten. Fixed: the success screen is reachable only via a path that
   awaits the server's real result.
3. **`null`-valued `hasExistingDomain` 400'd every autosave** while the domain
   question was unanswered, surfacing as a permanent, unexplained "sync error" pill.

## External setup still required

Nothing below blocks this release; it's what turns the in-app notification center
into real push:

1. Generate a Web Push VAPID key in the Firebase Console (Cloud Messaging → Web
   configuration).
2. Set it as a build-time environment variable (`NEXT_PUBLIC_FIREBASE_VAPID_KEY`).
3. Add a dedicated `firebase-messaging-sw.js` service worker and register for
   browser push events.
4. Browser notification permission grant, per device, from the user.

## Versioning policy

- **1.0.0 is frozen.** No new features land here.
- **`main` moves on as 1.1** — all new Discovery/Owner-Workspace/PWA/notification work
  builds on top of this release, not inside it.
- **Bug fixes to 1.0** are the one exception: a genuine defect in what's listed above
  gets fixed, tagged as `v1.0.x`, and — since this repo has no separate long-lived
  release branch — cherry-picked or reapplied to whatever `main` has become by then.
- Tag: `v1.0.0`, on the commit that merged
  [PR #46](https://github.com/Iantebi/pageloom-os/pull/46) into `main`.
